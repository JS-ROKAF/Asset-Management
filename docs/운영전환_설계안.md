# AssetHub 실운영 전환 설계안 (v1, 2026-10-26)

> **이 문서의 용도**: 개발 담당 Claude(코드베이스 직접 확인)가 작성한 설계안을 기획 담당 Claude에게 전달하기 위한 자기완결 문서.
> 읽는 쪽은 코드에 접근할 수 없다는 전제로 작성했다. 파일 경로는 근거 표시용이다.
> 코드·운영 DB는 아직 변경하지 않았다. 사용자가 이 설계안을 확인한 뒤 단계별로 구현을 요청할 예정이다.

---

## 0. 배경 요약

### 시스템 현황
- 사내 자산관리 웹앱. React 19(Vite) 프론트 + FastAPI 백엔드 + SQLite 단일 파일 DB(`db/assethub.db`)
- 사내망 고정 IP `192.168.0.189:8011` 전용. 이 PC에서 트레이 앱(`tray_AssetHub.py`)이 uvicorn 1개 프로세스로 화면+API를 함께 서빙
- 만들어 놓고 실제 운영한 적 없음. 운영 DB에는 테스트 데이터(자산 1건, 구성원 1건, 이력 0건)뿐이라 구조 변경 자유
- 주요 기능은 이미 있음: 자산 CRUD, 배정/반납 이력, 요청 승인, 정기 실사, QR(자산 1건씩), 엑셀 가져오기/내보내기, 소프트 폐기

### 회사·일정
- 법인 여러 개(두래, 두래티앤씨 등), 부서 수시 변경
- 대상: IT자산 약 200대(모니터·데스크탑·노트북) + 전화기·TV·복합기 등 약 30대. 이후 비품 확장 예정
- 일정: 11월 중순 기존 자산 이관 → 11월 하순 QR 라벨 부착 + 실사 → 2026-12-01 기준일 확정
- 기존 엑셀 대장이 망가진 최대 원인: **사용자 변경을 바로 기록하지 않음**. 기록이 쉽고 빠져나가지 않는 구조가 최우선

### 사용자 요구사항 (요약)
1. 마스터 데이터(법인/부서/유형/구성원) 관리 화면, 자산을 id(FK)로 연결, 자산 필드 추가(소유 법인, 구자산번호, 제조년월, 사양 CPU/RAM/저장장치/OS, 구매품의번호, 마지막 실사 확인일), 상태 재정의(사용중/공용/보관/수리중/분실, 폐기는 별도 유지), 상태 상수 일원화
2. 자산번호 자동 생성: `{법인코드}-{유형코드}-{4자리}` (예: D-NB-0001), 부서 미포함, 법인+유형별 연번, 번호 재사용 금지
3. 이력: "이동" 이력 추가, 기록자 저장, 이력 날짜 지정, 자산 상세에서 시간순 확인
4. 엑셀 가져오기 재작성(버그 수정, 전체 필드, 사번/이메일로 사용자 지정, 값 정리, 검증, 미리보기, 단일 트랜잭션, 드롭다운 양식) + 목록 내보내기
5. QR 라벨 A4 일괄 출력, 현장 QR 실사 시 즉석 정정(이력 자동 생성), 결과 확인/정정/미발견, 미발견 목록 내보내기
6. API 권한 검사, DB 잠금 버그 수정, 자동 백업, 실행·접속 구조 질문
7. 기타 운영 위험 지적

우선순위: 1단계(11/10) 데이터 구조·자산번호·가져오기·권한/잠금 → 2단계(11/20) QR·실사·내보내기·이력 → 3단계(12/1 이후) 백업 등

## 2. 핵심 설계 방향: 저장 로직을 서버로 이동

요구사항 대부분(기록자 저장, 단일 트랜잭션, 빠짐없는 이력, 동시 사용 안전)이 현재 "브라우저 diff → 행 덮어쓰기" 구조에서는 불가능하다.

- **변경**: 브라우저는 의도(사용자 변경, 이동, 상태 변경 등)만 전송. 서버가 한 트랜잭션에서 ① 규칙 검증 ② 자산 갱신 ③ 이력 생성(`recordedBy`=토큰 사용자, `recordedAt`=서버 시각). 저장 후 브라우저는 재조회(230건 규모라 부담 없음)
- 이력 생성 규칙이 서버 한 곳에만 존재 → "기록이 빠져나가지 않는 구조"의 실체
- 현재 diff 방식의 위험(필터된 배열을 넘기면 폐기 자산이 DB에서 실제 삭제됨)도 함께 제거
- 1단계의 최대 작업

## 3. 1단계 (11/10까지)

### 3-1. 테이블 구조

테스트 데이터뿐이라 새 스키마로 DB 재생성(기존 파일은 이름 변경해 보관, 교체 시점은 사용자 승인 후). 컬럼명은 프론트 관례대로 camelCase.

```
corporations   id PK, code TEXT NOT NULL UNIQUE (사용 중이면 수정 불가),
               name TEXT NOT NULL UNIQUE, active INT DEFAULT 1

departments    id PK, corporationId FK NOT NULL, name TEXT NOT NULL,
               active INT DEFAULT 1, UNIQUE(corporationId, name)

asset_types    id PK, code TEXT NOT NULL UNIQUE (사용 중이면 수정 불가),
               name TEXT NOT NULL UNIQUE,
               hasSpecs INT DEFAULT 0 (1이면 CPU/RAM/저장장치/OS 입력칸 표시),
               active INT DEFAULT 1

members        id INTEGER PK, employeeNo TEXT UNIQUE NULL (사번),
               email TEXT NOT NULL UNIQUE (로그인 ID), name NOT NULL,
               departmentId FK, position, permission CHECK(admin,manager,viewer),
               status CHECK(재직,퇴직), passwordHash
               ※ 소속 법인은 부서에서 파생 (중복 저장 시 불일치 위험)

assets         id TEXT PK (자산번호 D-NB-0001), legacyNo TEXT INDEX (구자산번호),
               name (비면 "유형 모델명"으로 표시), typeId FK NOT NULL,
               corporationId FK NOT NULL (소유 법인),
               departmentId FK (사용 부서, 소유 법인과 다를 수 있음),
               memberId FK (사용자), location,
               status NOT NULL CHECK(사용중,공용,보관,수리중,분실),
               CHECK((status='사용중') = (memberId IS NOT NULL)),
               model, serial UNIQUE (빈 값·"-"는 NULL 저장 → 중복검사 제외),
               manufacturedYm CHECK(YYYY-MM), purchaseDate, warrantyExpiry,
               purchaseCost INTEGER NULL (현재 TEXT라 합계 깨질 위험),
               vendor, approvalNo (구매품의번호), cpu, ram, storage, os, note,
               lastInspectedAt, createdAt, updatedAt (동시 수정 감지용),
               isDisposed, disposalMethod, disposalReason, disposalDate

asset_seq      PK(corporationId, typeId), lastNo INT   ← 번호 재사용 방지 카운터

history        id PK, assetId FK NOT NULL,
               type CHECK(입고,배정,반납,이동,상태변경,수리,실사정정,폐기),
               fromMemberId FK, toMemberId FK,
               detail (서버 생성 요약, 예 "위치: 3층 → 5층; 부서: A → B"),
               note (사용자 메모), eventDate NOT NULL (실제 발생일, 사용자 지정),
               recordedAt NOT NULL (서버 시각), recordedBy FK members NOT NULL

requests       requesterId, targetMemberId를 FK로 변경, 나머지 유지

inspections         id PK, title, status(진행중/종료), startedAt, endedAt, createdBy
inspection_checks   id PK, inspectionId FK, assetId FK,
                    result CHECK(확인,정정,미발견), checkedBy, checkedAt, note,
                    UNIQUE(inspectionId, assetId)
```

- 사용중⇔사용자 CHECK 제약: "사용중인데 사용자 없음", "보관인데 사용자 있음" 같은 불일치를 DB가 거부
- 마이그레이션 장치: `PRAGMA user_version` + 순서 있는 SQL 목록. 12/1 이후 실데이터가 생기면 "DB 삭제 후 재생성"이 불가능하므로 필요

### 3-2. 자산번호 규칙
- 자산 INSERT와 같은 트랜잭션에서 `asset_seq.lastNo + 1` 발급. 폐기·삭제돼도 번호 재사용 없음
- 수동 입력은 형식·법인코드·유형코드가 맞을 때만 허용, 카운터를 `max(lastNo, 입력번호)`로 올림
- **형식 의견**: 적절하다. 단 부서를 뺀 이유(이동 시 번호 틀어짐)가 법인 간 양도, 유형 오분류 정정에도 똑같이 적용된다 → 원칙: 번호는 바꾸지 않음(번호 = 최초 등록 기준. QR 라벨이 이미 부착되므로)
- 법인코드 **2글자 권장**(두래·두래티앤씨가 `D`로 충돌 가능 → 예 `DR`/`DT`). 유형코드도 2글자(`NB` `DT` `MN` `PH` `TV` `PR`)
- 4자리 = 법인+유형별 9,999대, 초과 시 자연히 5자리

### 3-3. 서버 쓰기 API

| 엔드포인트 | 한 트랜잭션 내 처리 |
|---|---|
| `POST /api/assets` | 번호 발급 + 입고 이력 + (사용자 있으면) 배정 이력 |
| `PATCH /api/assets/{id}` | 변경 필드 + eventDate + note + updatedAt 수신. 서버가 기존값과 비교해 배정/반납/이동/상태변경/수리 이력 생성. updatedAt 불일치 시 409 |
| `POST /api/assets/bulk` | 일괄 배정·반납·상태 변경·부서 이동 |
| `POST /api/assets/{id}/dispose` | 폐기 |
| `POST /api/members/{id}/retire` | 퇴직 + 보유 자산 반납(→보관) |
| `GET/POST/PATCH /api/masters/{corporations,departments,types}` | 기준정보. 삭제 없이 active 플래그만 |
| `POST /api/assets/import?dry_run=1` | 3-4 참고 |

### 3-4. 엑셀 가져오기
- 흐름: 브라우저가 SheetJS로 원본값만 읽어 전송 → 서버가 정리·검증(기존 DB와의 중복검사는 서버만 정확) → `dry_run=1` 응답을 미리보기로 표시(총 건수, 상태별 건수, 오류 목록 행·칸·사유) → 오류 0건일 때만 저장 활성 → 같은 엔드포인트로 저장(단일 트랜잭션, 실패 시 0건)
- 저장 직전 서버가 DB 자동 백업(sqlite backup API) — 이관 직후 되돌리기용 안전장치
- 양식 컬럼(`*` 필수):
  `자산번호, 구자산번호, 법인코드*, 유형코드*, 자산명, 모델명, 시리얼, 제조년월, CPU, RAM, 저장장치, OS, 취득일자, 취득금액, 구입처, 구매품의번호, 보증만료일, 부서, 위치, 상태*, 사용자(사번/이메일), 이력일자, 비고`
  - 부서: 부서명으로 찾음. 법인 간 같은 이름이 있으면 `DT/경영지원팀` 형식. 비어 있고 사용자가 있으면 사용자 부서로 채움
  - 이력일자: 비면 가져오기 당일
- 값 정리: 앞뒤 공백 제거 / 금액 `,` `원` `₩` 공백 제거 / 엑셀 날짜 일련번호 → `YYYY-MM-DD` / 제조년월이 일련번호면 → `YYYY-MM` (일반 서식 칸에 `2018-09` 입력 시 엑셀이 날짜로 자동 변환하는 경우 대응)
- 검증: 자산번호 중복(파일 내·DB), 시리얼 중복(파일 내·DB), 마스터에 없거나 비활성인 법인·부서·유형·구성원, 허용되지 않은 상태값, 상태–사용자 조합(사용중⇒사용자 필수, 공용·보관⇒사용자 없음), 날짜 형식
- **드롭다운 (결정 필요)**: 무료판 SheetJS는 데이터 유효성 생성 불가. 날짜 칸 텍스트 서식(`z:"@"`)은 가능
  - (a) 「코드표」 시트로 허용값 목록 제공 — 의존성 변화 없음 **(권장, 서버 검증이 오류를 행·칸 단위로 잡아줌)**
  - (b) 양식 생성용으로만 `exceljs` npm 추가

### 3-5. 권한·DB 잠금
- `helpers.py` 연결을 `with closing(...)` + `with conn:`으로 감싸 예외 시에도 연결 해제, 성공 시에만 commit

### 4-1. 이력 개선 — 서버 부분은 1단계로 당김 (동의 필요)
- 1단계 서버 API와 가져오기가 이미 이력을 생성한다. 이력 구조(이동·recordedBy·eventDate)가 1단계에 없으면 이관 이력이 기록자 없이 굳는다 → **스키마와 서버 이력 생성은 1단계에 포함**

### 4-2. QR 라벨 일괄 출력 (0.5일)
- 선택 자산 또는 필터 결과 전체를 A4 격자로. 라벨: QR + 번호 + 자산명 + 법인

### 4-3. 실사 흐름 (1.5일)
- 현재는 실사 시작 시 전체 자산을 항목으로 복사 → **변경: 확인한 것만 기록**. 진행률 = 확인 건수 / 활성 자산 수. 회차 종료 시 미확인 자산을 `미발견`으로 확정 기록 → 실사 도중 신규 등록 자산도 자연 포함

- 종료 시 **상태 자동 변경 안 함**(현재는 "없음"→미사용 자동, 그러나 미사용 상태가 사라지고 미발견≠분실). 미발견 목록 엑셀 내보내기 + 목록에서 [분실 처리] 일괄 버튼으로 사람이 판단

## 7. 실행·접속 구조와 동시 사용 (사용자 질문 6번 답)

**실행 구조**: 이 PC(`192.168.0.189`)에서 `tray_AssetHub.py`가 uvicorn 1프로세스 실행, 화면+API를 `:8011`로 통합 서빙. 직원은 같은 사내망에서 브라우저로 접속(설치 불필요). 같은 PC에 PTO·DuraeKPI·HrAgent 공존

**PC가 꺼지면**: 전원 접속 불가. 트레이는 Windows 사용자 세션 앱이라 재부팅 후 로그인 전·절전·로그오프 시에도 중단. 자동 시작 미등록 상태(확인함). 대책: 최소 = 절전 해제 + 작업 스케줄러 "로그온 시 실행" / 확실 = 서비스 등록(NSSM 등) 또는 상시 가동 전용 PC. DB가 파일 1개라 디스크 고장 시 소실 → 외부 백업 필요

**동시 사용**:
- DB 쪽은 문제 없음 — SQLite WAL + 단일 프로세스로 수십 명 규모 충분
- **앱 구조 문제로 현재는 동시 사용 시 데이터가 조용히 틀어짐**:
  1. 로그인 시 1회 로드 후 재조회 없음 → 남의 변경이 안 보임
  2. 수정 시 행 전체 PATCH → 오래된 화면에서 저장하면 남이 바꾼 값을 경고 없이 되돌림
  3. 자산 저장과 이력 저장이 별도 요청 → 반쪽 저장 가능
  4. 이력 시각이 각자 PC 시계
  5. 권한·부서가 JWT에 8시간 고정 → 변경 시 재로그인해야 반영
- 1~4는 1단계 서버 API 전환(저장 후 재조회 + updatedAt 비교 409)으로 해결. 5는 권한 변경 시 재로그인 안내로 충분
