## 0. 배경 요약

### 시스템 현황
- 사내 자산관리 웹앱. 구성은 React 19(Vite) 프론트 + FastAPI 백엔드 + SQLite 단일 파일 DB(`db/assethub.db`)
- 사내망 고정 IP `192.168.0.189:8011` 전용. 이 PC의 트레이 앱(`tray_AssetHub.py`)이 uvicorn 프로세스 1개로 화면과 API를 함께 서빙
- 아직 운영한 적 없음. 운영 DB에는 테스트 데이터만 있음(자산 1, 구성원 1, 이력 0). 구조 변경 자유
- 이미 있는 기능: 자산 CRUD, 배정/반납 이력, 요청 승인, 정기 실사, QR(자산 1건씩), 엑셀 가져오기/내보내기, 소프트 폐기

### 회사·일정
- 법인: 두래(DR), 두래티앤씨(TC), 셀럭스(SL). 부서는 수시로 바뀜
- 대상 규모: IT자산 약 200대 + 전화기·TV·복합기 약 30대. 이후 비품까지 확장 예정
- 🆕 이관 원천 데이터: 설문 121대 + 기존 대장 5개 파일. 이 중 약 60대는 현재 사용자를 알 수 없어 "미확인"으로 이관
- 일정: 11월 중순 이관 → 11월 하순 QR 라벨 부착 + 실사 → 2026-12-01 기준일 확정 (목표: 이 시점 미확인 0건)
- 가장 중요한 원칙: 사용자 변경이 빠짐없이, 쉽게 기록되는 구조

## 2. 핵심 방향: 저장 로직을 서버로 이전 (합의됨)

- 브라우저는 하려는 작업만 보낸다. 서버가 한 트랜잭션 안에서 검증 → 자산 갱신 → 이력 생성(recordedBy = 토큰 사용자, recordedAt = 서버 시각)까지 처리한다. 브라우저는 저장 후 다시 조회한다.
- 이력 생성 규칙은 서버 한 곳에만 둔다.
- 기존 diff 방식에서 폐기 자산이 실제로 삭제되던 위험도 함께 사라진다.

## 3. 1단계 (11/10까지)

### 3-1. 테이블 구조

새 스키마로 DB를 다시 만든다. 기존 파일은 이름만 바꿔 보관하고, 교체 시점은 사용자 승인을 받는다. 컬럼명은 camelCase를 쓴다.

```
corporations   id PK, code TEXT NOT NULL UNIQUE (사용 중이면 수정 불가),
               name TEXT NOT NULL UNIQUE, active INT DEFAULT 1
               초기값: DR 두래 / TC 두래티앤씨 / SL 셀럭스

departments    id PK, corporationId FK NOT NULL, name TEXT NOT NULL,
               active INT DEFAULT 1, UNIQUE(corporationId, name)

asset_types    id PK, code TEXT NOT NULL UNIQUE (사용 중이면 수정 불가),
               name TEXT NOT NULL UNIQUE, hasSpecs INT DEFAULT 0, active INT DEFAULT 1
               초기값: 부록 A

members  ✏️    id INTEGER PK (내부 키, FK 대상),
               employeeNo TEXT NOT NULL UNIQUE (사번, 기준 키, 인사 연동 키)  ✏️
               email TEXT UNIQUE NULL (선택. SQLite에서 NULL은 여러 개 허용)  ✏️
               name NOT NULL, departmentId FK, position,
               permission TEXT NULL CHECK(admin,manager,viewer)  ✏️
                  NULL = 로그인 불가인 일반 구성원(자산 사용자)
               status CHECK(재직,퇴직), passwordHash
               소속 법인은 부서에서 파생

assets         id TEXT PK (자산번호 DR-NB-0001),
               legacyNo TEXT INDEX (구자산번호. UNIQUE 아님. 같은 번호 중복 허용, 검색 대상)
               name, typeId FK NOT NULL, corporationId FK NOT NULL (소유 법인),
               departmentId FK, memberId FK, location,
               status NOT NULL CHECK(사용중,공용,보관,수리중,분실,미확인)  ✏️
               CHECK((status='사용중') = (memberId IS NOT NULL))
                  → 미확인·공용·보관·수리중·분실은 사용자 없음
               model, serial UNIQUE (빈 값과 "-"는 NULL로 저장),
               manufacturedYm CHECK(YYYY-MM),
               purchaseDate CHECK(YYYY-MM 또는 YYYY-MM-DD)  ✏️
               warrantyExpiry CHECK(YYYY-MM-DD), purchaseCost INTEGER NULL,
               vendor, approvalNo, cpu, ram, storage, os, note,
               lastInspectedAt, createdAt, updatedAt,
               isDisposed, disposalMethod, disposalReason, disposalDate

asset_seq      PK(corporationId, typeId), lastNo INT

history        id PK, assetId FK NOT NULL,
               type CHECK(입고,배정,반납,이동,상태변경,수리,실사정정,폐기),
               fromMemberId FK, toMemberId FK, detail, note,
               eventDate NOT NULL (실제 발생일), recordedAt NOT NULL (서버 시각),
               recordedBy FK members NOT NULL

requests       requesterId, targetMemberId를 FK로 변경, 나머지는 유지

inspections         id PK, title, status(진행중/종료), startedAt, endedAt, createdBy
inspection_checks   id PK, inspectionId FK, assetId FK, result CHECK(확인,정정,미발견),
                    checkedBy, checkedAt, note, UNIQUE(inspectionId, assetId)
```

- 스키마 버전 관리: `PRAGMA user_version` + 순서가 있는 SQL 목록
- 💬 **미확인 상태와 사용자**: 미확인은 "사용자를 모름"이라는 뜻이므로 memberId는 NULL로 둔다. 대장에 이름은 있지만 확실하지 않은 경우에는 그 이름을 비고에 적는다(예: `대장상 사용자: 홍길동`). 그러면 실사 담당자가 현장에서 참고할 수 있다.
- 💬 **purchaseDate가 `YYYY-MM`일 때의 계산**: 경과기간 계산과 정렬은 그 달 1일로 간주한다. 보증만료일은 경고 계산에 쓰이므로 `YYYY-MM-DD`만 허용한다(요청에 없어 v1과 같게 유지).

### 3-2. 자산번호
- 형식은 `{법인코드}-{유형코드}-{4자리}`이다. 예: `DR-NB-0001`, `TC-PC-0012`, `SL-PH-0003`
- 자산 INSERT와 같은 트랜잭션에서 `asset_seq`로 발급한다. 같은 번호는 재사용하지 않는다.
- 수동 입력 번호는 형식·법인코드·유형코드가 맞아야 받는다. 받은 경우 카운터를 `max(lastNo, 입력번호)`로 올린다.
- 법인 양도나 유형을 정정해도 번호는 바꾸지 않는다. 번호는 최초 등록 시점 기준이다.

### 3-3. 서버 쓰기 API

| 엔드포인트 | 한 트랜잭션 안에서 처리하는 내용 |
|---|---|
| `POST /api/assets` | 번호 발급 + 입고 이력 + (사용자가 있으면) 배정 이력 |
| `PATCH /api/assets/{id}` | 변경 필드 + eventDate + note + updatedAt을 받는다. 서버가 이력을 생성한다. updatedAt이 다르면 409 |
| `POST /api/assets/bulk` | 일괄 배정, 반납, 상태 변경, 이동 |
| `POST /api/assets/{id}/dispose` | 폐기 |
| `POST /api/members/{id}/retire` | 퇴직 처리 + 보유 자산 반납(→ 보관) |
| `GET/POST/PATCH /api/masters/{corporations,departments,types}` | 기준정보. active 플래그만 쓰고 삭제는 하지 않음 |
| `POST /api/assets/import?dry_run=1` | 3-4 참고 |
| 🆕 `POST /api/members/import?dry_run=1` | 구성원 일괄 등록. 사번 기준, 오류 미리보기 방식은 자산 가져오기와 같음 |

### 3-4. 엑셀 가져오기 ✏️

- **흐름**: 브라우저가 원본 값을 읽어 전송 → 서버가 정리·검증 → `dry_run` 결과로 미리보기(총 건수, 상태별 건수, 오류 목록: 행·칸·사유) → 오류가 0건일 때만 저장 → 단일 트랜잭션으로 저장. 저장 직전에 서버가 DB를 자동 백업한다.
- 🆕 **가져오기 순서**: 기준정보(법인·부서) → 구성원(사번) → 자산. 자산 양식의 사용자는 사번으로 찾기 때문에, 구성원이 먼저 등록되어 있어야 한다. 대장에 있는 퇴사자나 외부인처럼 구성원 목록에 없는 사람은 오류로 표시된다. 이런 기기는 미확인이나 보관으로 넣고, 이름은 비고에 적는다.

**자산 양식 컬럼** (`*` = 필수, ✏️ = v2 변경)

`자산번호, 구자산번호, 법인코드*, 유형코드*, 자산명, 모델명, 시리얼, 제조년월, CPU, RAM, 저장장치, OS, 취득일자, 취득금액, 구입처, 구매품의번호, 보증만료일, 부서, 위치, 상태*, 사용자(사번)✏️, 지급일🆕, 이력일자, 비고`

- 사용자: 사번만 받는다(이메일로 찾기는 없앰).
- 🆕 **지급일**: 사용자가 있을 때만 쓸 수 있다. 사용자 없이 지급일만 있으면 오류다.
- **이력 생성 규칙** ✏️
  - 입고 이력: eventDate = 가져온 날(고정)
  - 배정 이력(사용자가 있을 때): eventDate = 지급일 → 없으면 이력일자 → 없으면 가져온 날
- 💬 **이력일자 칸 존치 여부**: 입고가 가져온 날로 고정되었으므로, 이력일자 칸은 지급일이 비었을 때 배정 이력의 날짜로만 쓰인다. 두 칸이 사실상 같은 역할이다. **이력일자 칸을 없애고 "지급일이 비면 가져온 날"로 단순화할 것을 권장한다.** 결정 전까지는 위 규칙대로 둘 다 유지한다.
- 💬 **타임라인 표시**: 지급일이 과거이면 배정(예: 2023-03)이 입고(2026-11)보다 앞에 표시된다. 이는 "2023년부터 사용, 2026년 시스템 등록"이라는 사실 그대로다. 다만 화면에서는 입고 이력의 메모를 `시스템 이관 등록`으로 고정해서 오해를 줄인다. 2단계에 넣을 "과거 날짜 경고" 규칙은 가져오기에는 적용하지 않는다.
- **상태와 사용자 조합 검증**: 사용중이면 사용자 필수. 공용·보관·수리중·분실·미확인이면 사용자가 없어야 한다.
- **값 정리** ✏️
  - 공통: 앞뒤 공백 제거
  - 금액: `,` `원` `₩` 공백 제거
  - 날짜 칸(취득일자·보증만료일·지급일·이력일자): 엑셀 일련번호를 `YYYY-MM-DD`로 변환
  - **취득일자와 제조년월**: 텍스트 `YYYY-MM`은 그대로 둔다. 일련번호가 1일 자정이면 `YYYY-MM`으로 변환한다.
    - 💬 일련번호만으로는 원래 `2018-09`라고 입력했는지 `2018-09-01`이라고 입력했는지 구분할 수 없다.
    - 위 규칙대로 하면 실제로 "1일"인 취득일도 월 단위로 저장된다. 정보 손실은 거의 없다.
    - 양식에서 날짜 칸은 텍스트 서식이므로 대부분은 이 규칙까지 가지 않는다.
- **검증 항목**: 자산번호 중복(파일 안·DB), 시리얼 중복(파일 안·DB, 빈 값과 "-" 제외), 마스터에 없거나 비활성인 법인·부서·유형, 없는 사번이나 퇴직자 사번, 상태값, 상태–사용자 조합, 날짜 형식
  - 구자산번호는 중복을 검사하지 않는다.
- **양식 파일**: 「자산목록」 시트(예시 1행, 날짜 칸 텍스트 서식) + 「코드표」 시트(법인코드, 부서, 유형코드, 상태 허용값). 코드표는 다운로드 시점의 마스터 데이터로 만든다.
- **법인 추정값**: 별도로 처리하지 않는다. 기획 측이 추정한 값을 넣고 비고에 "법인 추정"이라고 적는다.

**구성원 양식** 🆕: `사번*, 이름*, 법인코드*, 부서*, 직급, 이메일, 재직상태`
- 권한과 비밀번호는 양식에 넣지 않는다. 화면에서 admin이 따로 부여한다.

### 3-5. 권한·로그인·DB 잠금 ✏️
- 연결 처리를 `with closing` + `with conn:`으로 정리한다. 예외가 나도 연결이 닫히고, 성공했을 때만 commit한다.
- 쓰기 엔드포인트 전체에 권한을 지정한다.
  - 기준정보와 권한 변경: admin만
  - 자산 쓰기: admin과 manager
  - manager는 자기 부서 자산만(서버에서 검사)
- JWT 비밀키: 첫 실행 시 무작위로 생성해 파일로 저장한다(git 제외). bootstrap 응답에서 passwordHash를 뺀다.
- 🆕 **로그인 ID를 email에서 사번으로 변경**: email이 선택 항목이 되었으므로 로그인 키는 사번이다. 로그인 조건은 세 가지다.
  - permission이 NULL이 아님
  - passwordHash가 있음
  - 재직 중
  - 임시 비밀번호는 permission이 있는 구성원에게만 발급할 수 있다.
- 💬 **기존 admin 계정**: 현재 로그인 ID는 `admin`(email 칸)이다. 기본안은 사번을 `admin`으로 두는 **시스템 계정**이며, 인사 연동 대상에서 제외한다. 실제 담당자의 사번을 쓰려면 알려 달라.
- 💬 **인사 연동 대비**: 연동 방식은 나중에 요청받기로 했으므로 지금은 아무것도 만들지 않는다. 다만 다음 원칙은 지킨다.
  - 내부 id와 사번을 분리한다. 사번이 바뀌어도 자산·이력 FK가 유지된다.
  - permission과 passwordHash는 AssetHub만 관리하는 칸으로 둔다. 연동 시 덮어쓰지 않게 하기 위해서다.

### 4-2. QR 라벨 일괄 출력 ✏️ (0.75일)
- 선택한 자산 또는 필터 결과 전체를 A4에 격자로 배치한다. 인쇄 CSS와 `window.print()`를 쓰고 새 라이브러리는 추가하지 않는다.
- 🆕 **라벨 구성**: 자산번호를 **글자로 크게** 인쇄한다(라벨 높이의 약 1/3, 굵게). QR이 손상돼도 번호로 찾을 수 있다. 그 밖에 QR, 자산명, 법인을 넣는다.
- 용지 규격(칸 수, 칸 크기, 여백)은 코드 상단 상수 한 곳에 둔다. 규격이 정해지면 그 값만 넣으면 된다.
  - 예시 규격 64×34mm라면 QR 약 28mm + 오른쪽 글자 영역 구성이 가능하다.
- 🆕 **QR 주소를 서버 설정값 1개로 고정** 💬
  - 지금은 출력할 때 `window.location.origin`을 쓴다.
  - 그래서 개발 서버(`:5173`)나 다른 주소로 접속해 출력하면 **엉뚱한 주소가 라벨에 영구히 인쇄된다.**
  - 수정: 서버 설정 `QR_BASE_URL` 하나를 두고, 라벨과 단건 QR이 모두 이 값을 쓰게 한다.
- **QR 주소 선택지별 작업**

| 선택 | 필요한 작업 |
|---|---|
| IP 고정 유지 | 없음. `QR_BASE_URL=http://192.168.0.189:8011`. 대신 IP와 포트를 영구히 유지해야 함 |
| 사내 도메인 | ① 사내 DNS(공유기 또는 AD)에 이름 등록 ② `QR_BASE_URL` 변경 ③ CORS 허용 목록 추가 ④ CLAUDE.md의 "도메인 미지원" 정책 개정. 포트를 빼려면 80 포트 사용 가능 여부도 확인 필요(같은 PC에서 PTO 등이 구동 중). 장점: PC나 IP가 바뀌어도 DNS만 고치면 라벨은 그대로 사용 가능 |

- 💬 라벨 수명을 생각하면 **사내 도메인을 권장한다.** 단, 사내 DNS를 운영할 수 있어야 한다.

### 4-3. 실사 흐름 ✏️ (2일)
- 확인한 것만 기록한다. 진행률 = 확인 건수 / 활성 자산 수. 회차를 종료할 때 확인하지 않은 자산을 미발견으로 확정한다.
- 현장 QR 화면에서 할 수 있는 일
  - [확인]
  - [정정]: 사용자·위치·부서·상태를 고치면 서버가 한 트랜잭션으로 처리한다(자산 갱신 + 실사정정 이력 + check 기록 + lastInspectedAt).
- 🆕 **미확인 자산을 스캔하면 [확인] 버튼이 없다.** [정정]만 나오고, 상태 선택은 필수다(미확인 외의 값). 이렇게 하면 "봤다"고만 누르고 미확인으로 남는 경우가 생기지 않는다.
- 회차를 종료해도 상태는 자동으로 바꾸지 않는다. 미발견 목록 내보내기 + [분실 처리] 일괄 버튼을 제공한다.
- 🆕 **종료 화면**
  - 경고 표시: 남은 미확인 N건, 미발견 N건. 미확인이 0이 아니어도 종료는 할 수 있다.
  - **[기초 자산대장 내보내기]**: 종료 시점의 전체 자산(폐기 제외)을 내보낸다. 마스터 이름을 풀어 쓰고, 사양·구번호·이번 회차 실사 결과·확인일을 포함한다.
    - 파일명 예: `기초자산대장_{회차명}_{종료일}.xlsx`
    - 종료 후에도 같은 회차 화면에서 다시 내려받을 수 있다. 실사 결과는 회차 기록 기준이다. 다만 자산 정보는 내려받는 시점의 값이 된다.
  - 🆕 **종료 시 서버가 DB를 자동 백업한다**(`inspection_{id}_close`). 엑셀 파일을 잃어버려도 그 시점의 원본 DB로 다시 만들 수 있다. 이 백업은 자동 삭제 대상에서 제외한다.

### 4-5. 🆕 백업과 자동 시작 (3단계에서 이동, 1일)
- **백업**
  - `sqlite3.Connection.backup()`으로 교체한다.
  - Windows 작업 스케줄러에 매일 실행으로 등록한다(이 PC의 `DuraeKPI_DbBackup` 작업과 같은 방식).
  - 보관 기간은 `KEEP_DAYS`로 정한다. 실사 종료 백업은 제외한다.
  - 로컬 백업 후 외부 경로로 복사한다.
- 💬 **외부 경로 주의**: 작업 스케줄러가 "로그온 여부와 관계없이 실행"으로 돌면 네트워크 공유에 접근할 자격증명이 따로 필요하다. 경로가 정해지면 등록할 때 실제로 복사되는지 확인한다.
  - 외부 복사가 실패해도 로컬 백업은 남는다.
  - 실패 기록은 로그 파일에 남긴다.
- **자동 시작**
  - 작업 스케줄러에 "로그온 시 실행"을 등록하고 절전을 해제한다.
- 💬 이 방식은 **누군가 이 PC에 로그온해야** 서버가 뜬다. 재부팅 후 아무도 로그인하지 않으면 계속 멈춰 있다. 이게 문제가 된다면 서비스 등록(NSSM 등)이 필요하다. 그 경우 트레이 아이콘은 쓸 수 없다.

- 부서는 기획 측 데이터로 등록한다. 현재 코드에 하드코딩된 7개 부서는 법인 소속이 정해져 있지 않아 초기값으로 쓰지 않는다.
- 💬 기존 유형 중 키보드/마우스, 네트워크 장비, 비품, 차량은 목록에서 빠졌다. 필요해지면 기준정보 화면에서 추가할 수 있다.
- 💬 셀럭스: 현재 코드에서는 "셀럭스"가 **부서**로 들어가 있다. v2부터는 **법인**이다. 셀럭스 안의 부서는 기획 측 부서 목록에 포함해야 한다.

## 제약
- 운영 DB(`db/assethub.db`)는 사용자 승인 전까지 손대지 않는다. 테스트는 복사본으로만 한다.
- 외부 도메인 요청 0건을 유지한다. 라이브러리는 npm으로 번들하고 CDN은 쓰지 않는다.
- 현재 접속은 사내망 `192.168.0.189:8011` 전용이다(도메인을 선택하면 정책을 개정).
- 회계·세무는 범위 밖이다.
